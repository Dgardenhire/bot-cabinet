# Turn customer feedback into useful bug reports

Designed for: Small software teams sorting complaints and feature requests

Result: Draft issues that separate reported symptoms, reproduction evidence and feature requests.

## Try a sample first

Illustrative example, not a recorded Bot run. This adaptation has not been runtime-tested.

### Complete first request

Group the supplied customer feedback, preserve source references, and draft issues. Distinguish reports from reproduced failures and new features. Remove private details and ask before posting Use only the records I supply. Label missing or uncertain information. Do not connect accounts, browse, send, submit, publish, spend money or create a schedule. Return a draft for my review.

Fictional feedback. F1: 'Export fails after I choose CSV on my phone.' F2: 'Please add XLSX export.' F3: 'CSV download is blank on mobile.' No device, browser, logs or reproduction steps are supplied.

### Example result

Possible related bug reports: F1 and F3, mobile CSV export; relationship unconfirmed and not reproduced. Request browser, device and steps. Separate feature request: XLSX export (F2). Prepare two drafts; do not open issues or claim a fix.

### Check the answer

- Keep a requested feature separate from a suspected bug.
- Do not call the failure reproduced.
- Do not post issues or change code.

## Operating guide

- **When to use it:** Use this workflow when you need draft issues that separate reported symptoms, reproduction evidence and feature requests.
- **Lead Bot:** Coder
- **Cadence:** When a new request arrives and a person assigns it
- **Typical first run:** 15–30 minutes for a first manual run

### Access for the first run

- The approved inputs listed on this page
- Only the files, sources, and services required for this run
- No sending, publishing, spending, or live-system changes without approval
